# Phase 2: Detection

The orchestrator scans the in-scope files (per `scope_files.txt` from Phase 0) for the five artifact categories below, using the embedded catalog at `references/artifact-catalog.md` plus the Phase 1 web research findings. Output: `.mz/task/<task_name>/detection.md`.

This phase runs in the orchestrator itself — no subagent dispatch — because detection is regex/grep work and the user must see the consolidated hit list at the approval gate. Subagent latency adds nothing.

## 2.1 Load the catalog

Use Grep against `references/artifact-catalog.md` for the per-category pattern blocks. Do not read the entire file. The catalog uses these grep anchors:

- `# Category A:` — AI signatures & watermarks
- `# Category B:` — Pipeline phase markers
- `# Category C:` — Planning / generation-process comments
- `# Category D:` — WHAT-not-WHY comments
- `# Category E:` — Dead code & half-implementations

For each category fetch its block, parse the regex list, and combine with category-matching entries from `.mz/task/<task_name>/web_research.md` (if `research_status: complete`).

## 2.2 Scan in-scope files

For every file path in `.mz/task/<task_name>/scope_files.txt`:

1. **Skip binary files** — match by extension (`.png`, `.jpg`, `.pdf`, `.zip`, `.so`, `.dll`, etc.). Detect text-vs-binary via first 8KB if the extension is ambiguous.
2. **Skip excluded markdown directories** — already filtered in Phase 0, but re-check here: `docs/`, `guidelines/`, repo-root `README.md`, this skill's own `references/`. The user can override via explicit path argument, but the default scan never touches them.
3. **Run grep per category** — use `Bash` with `grep -nE` (extended regex, line numbers) for each pattern. Collect hits as `(category, pattern_id, file_path, line_number, matched_text)` tuples.

Use parallel `Bash` calls when scope is large (`files_in_scope > 50`), one grep invocation per category across the whole scope.

## 2.3 Category-specific detection rules

### A. AI signatures & watermarks

Pattern sources: catalog + research. Common exact strings:

- `🤖 Generated with [Claude Code]` / `🤖 Generated with Claude Code`
- `Co-Authored-By: Claude <noreply@anthropic.com>`
- `https://claude.ai/code` (when inside source files, not in legitimate doc links)
- `<!-- Generated by Cursor -->`, `// generated by Copilot`, `# aider:`, `# codex:`
- Identity claims: "I am Claude", "as a large language model", "I was asked to"

False-positive guard: skip matches inside string literals that look like fixture data or test expectations (heuristic: line ends with `"` or `'` in test files).

### B. Pipeline phase markers

Regex anchors (from catalog):

- `Phase \d+(\.\d+)?:` inside any comment.
- Literal `<task_name>` placeholder substring.
- `.mz/task/`, `.mz/reports/`, `.mz/research/` path tokens in non-pipeline source files (allow inside this skill's own files and inside `plugins/*/skills/*/SKILL.md` / `phases/` files).
- `STATUS: DONE`, `STATUS: NEEDS_CONTEXT`, `STATUS: BLOCKED` outside agent definition files.
- "dispatched by", "per pipeline plan", "from planner", "expert-*-agent" (any agent role) in source-code comments.

### C. Planning / generation-process comments

Regex anchors:

- `//\s*per\s+plan`, `//\s*from\s+research`, `//\s*per\s+the\s+plan\s+we`
- `//\s*TODO\s+from\s+planning`, `//\s*implementation\s+per\s+phase\s+\d`
- `/\*\s*Plan:\s*\d`, `/\*\s*AI\s+generated\s*\*/`
- `//\s*generated\s+by\s+AI`, `//\s*model:\s*(opus|sonnet|haiku)`
- `//\s*per\s+user\s+approval`, `//\s*after\s+user\s+approved\s+phase`

Apply to all comment styles: `//`, `#`, `/* */`, `<!-- -->`, language-appropriate.

### D. WHAT-not-WHY comments (conservative)

This category requires per-instance judgment by the cleaner agent. The orchestrator only flags candidates:

1. **Restated-code candidate** — a single-line comment immediately above a code line where the comment's tokenized content overlaps ≥ `WHAT_WHY_SIMILARITY_THRESHOLD` (0.7) with the identifiers/keywords in the next non-blank line.
2. **Echo-the-name docstring** — first line of a docstring inside `def`/`function`/`fn` declarations whose tokens overlap ≥ 0.7 with the function name (split on underscores/camelCase).
3. **Trivial inline label** — a one-or-two-word comment at end of an obvious operation: `// add`, `// subtract`, `// return result`, `// loop`, `// check`.

Tokenization: lowercase, split on non-alphanumeric, drop stop words (`the`, `a`, `is`, `to`, `of`, `for`, `and`, `with`).

Mark each candidate in `detection.md` with `decision: pending` — the cleaner agent decides per-instance whether the comment captures genuine WHY (regulatory note, perf workaround, surprising-behavior callout).

### E. Dead code & half-implementations

Regex / structural anchors:

- ≥ 3 consecutive lines starting with the language's line-comment prefix where the inner text contains code-like tokens (`=`, `function`, `def`, `class`, `import`, `(`, `)`, `;`).
- `TODO:\s*implement`, `FIXME:\s*stub`, `pass\s+#\s*TODO`, `throw\s+new\s+NotImplementedError`.
- Stale `// removed:` / `// deleted:` / `// REMOVED:` markers older than the file's most-recent edit (heuristic: orphaned references with no surrounding context).
- Empty function bodies: `def \w+\([^)]*\):\s*\n\s*pass\s*#?\s*TODO` (Python), `function \w+\([^)]*\) \{\s*\}` (JS).
- Unused imports — defer to the project linter (ruff, eslint, etc.), not orchestrator-side. Note as `category: E, source: linter` only when the verification phase runs the linter.

## 2.4 Severity classification

Total category-A + B + C hits drives severity for AI-leftover specifically. D and E feed into a separate count because their handling is conservative.

| Severity        | A+B+C hits | D+E hits | Cleanup intensity                                        |
| --------------- | ---------- | -------- | -------------------------------------------------------- |
| **Light**       | 1–10       | 0–10     | Single cleaner wave; auto-delete A/B/C; review D/E.      |
| **Medium**      | 10–50      | 10–30    | One or two waves; full review of D/E candidates.         |
| **Heavy**       | > 50       | > 30     | Up to MAX_FIX_ITERATIONS waves; staged file-by-file.     |

When the file count is small (< 5) but hits are high, treat as Medium minimum to avoid one cleaner agent doing all the work in one shot — split for safety.

## 2.5 Write detection.md

Structure:

```markdown
# Leftover Artifact Detection — <task_name>

## Scope
- Mode: <working|branch|global>
- Files in scope: <N>
- Excluded (markdown docs): <N>
- Research: <complete|unavailable>

## Severity: <Light|Medium|Heavy>
- A+B+C total: <N>
- D+E total: <N>
- Cleaner waves planned: <N>

## Category A — AI signatures & watermarks (<N> hits)
- `path/to/file.py:42` — `🤖 Generated with Claude Code`
- ...

## Category B — Pipeline phase markers (<N> hits)
- `path/to/file.ts:17` — `// Phase 2: validation`
- ...

## Category C — Planning / generation comments (<N> hits)
- ...

## Category D — WHAT-not-WHY candidates (<N> flagged, decision pending)
- `path/to/file.py:88` — `// increment counter` (next line: `i += 1`)
  - Token overlap: 0.83
  - Cleaner decides: keep|delete
- ...

## Category E — Dead code & half-implementations (<N> hits)
- `path/to/file.py:120-128` — 9-line commented-out block (function definition)
- `path/to/file.js:55` — `throw new NotImplementedError("TODO")`
- ...

## Proposed Cleanup Plan
- Category A/B/C: auto-delete in <N> cleaner waves across <M> files.
- Category D: cleaner reviews each candidate; deletes when token overlap ≥ 0.7 AND no WHY content (numbers, units, names, "because", "due to", "to avoid"); keeps otherwise.
- Category E: cleaner deletes commented-out blocks ≥ 3 lines unless adjacent to active code that references the block; replaces NotImplementedError stubs only if marked `decision: delete-stub` in the per-file plan; defers unused imports to the linter in Phase 4.

## Files excluded
- `<path>` — reason (markdown doc, vendored, generated, this skill's references).
```

Keep `detection.md` under 1000 lines. If hits exceed this, summarize per-category and write the full hit list to `.mz/task/<task_name>/detection_hits.json` (JSON array of tuples); reference the JSON file from `detection.md`. The approval gate still presents `detection.md` verbatim.

## 2.6 Hand off to Phase 2.5

Update `state.md`:

- `Phase: 2.5`
- Append `detection.md` (and `detection_hits.json` if used) to `FilesWritten`.
- Set `severity: light|medium|heavy`, `hits_abc: <N>`, `hits_de: <N>`.

Phase 2.5 (approval gate) runs next, defined inline in SKILL.md.
