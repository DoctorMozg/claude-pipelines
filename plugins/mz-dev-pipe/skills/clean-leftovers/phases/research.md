# Phase 1: Research (Mandatory)

The orchestrator dispatches `pipeline-web-researcher` (mz-dev-pipe plugin) to refresh the current catalog of AI code-tells and tool watermarks. Research is mandatory because tool watermark strings and AI-signature footers shift on a multi-month cadence; relying on the embedded list alone is how stale detection gets shipped to PR review.

Output: `.mz/task/<task_name>/web_research.md`. The orchestrator merges these findings with `references/artifact-catalog.md` (lazy-loaded by grep in Phase 2) when scanning.

## 1.1 Dispatch the researcher

Single dispatch, model `sonnet`. The brief:

```
Topic: Current AI-generation leftover artifacts in CODE files (not prose) — 2025-2026 data.

Sources to prioritize:
  - Official tool documentation: Claude Code, Cursor, GitHub Copilot, Aider, Codex CLI, ChatGPT Code Interpreter, Codeium, Tabnine, Continue.dev.
    Look specifically for the EXACT strings they write into commits, comments, or generated files (footers, attribution lines, watermarks).
  - Tool release notes / changelogs for the past 12 months — watermark formats change between major versions.
  - Public PR review threads complaining about AI artifacts leaking into commits (GitHub search: "Generated with Claude Code", "Co-Authored-By: Claude", "Generated by Copilot", "🤖 Generated").
  - Repository .gitattributes / pre-commit configs that strip AI watermarks — these expose the exact strings teams scrub.

Banned: AI-generated detection sites, undated blog speculation, social-media screenshots.

Output a structured list:
  A. AI signatures & watermarks   — exact strings + the tool that emits them + which file types they appear in.
  B. Pipeline phase markers       — emerging conventions from agent pipelines (Phase N: notation, dispatch leftovers, state-machine breadcrumbs).
  C. Planning/generation comments — patterns where AI restates its plan in comments ("// per plan", "// implementation per phase N", "// generated by AI").
  D. WHAT-not-WHY comments        — recent academic / industry research on AI-comment patterns vs. human comments (token-overlap heuristics, restatement signatures).
  E. Dead code / half-implementations — AI stub patterns (NotImplementedError shells, TODO: implement, pass # TODO).

For each item include: the exact regex or substring; one real-world example; the tool/source that emits it; first-observed date if known.

Output path: .mz/task/<task_name>/web_research.md

Banned in output: any item not grounded in a cited source. Mark items with "no source — embed only" if they come from your own knowledge.
```

Wait for completion. The researcher writes `web_research.md` directly.

## 1.2 Handle failures

If the dispatch returns `BLOCKED` (e.g., no web access in the runtime) or `NEEDS_CONTEXT`:

1. Retry once with the same brief.
1. If the second attempt fails, write `.mz/task/<task_name>/web_research.md` with the single line `RESEARCH UNAVAILABLE — embedded catalog only.` and continue.
1. Append a flag to `state.md`: `research_status: unavailable`. The final report (`phases/verification.md`) surfaces this so the user knows detection ran without fresh patterns.

Do not block the pipeline on research failure. Stale detection is better than no detection.

## 1.3 Validate the research output

After the dispatch completes, the orchestrator reads `web_research.md` and runs a minimal sanity check:

- File exists and is non-empty.
- Contains at least one section header matching categories A–E (or the `RESEARCH UNAVAILABLE` fallback line).
- No category-A entry without a cited source (uncited tool watermarks lead to false positives).

If validation fails, retry the dispatch once with the additional instruction: `Previous output failed validation: <reason>. Re-emit with all five categories and at least one cited source per category-A entry.`

## 1.4 Hand off to Phase 2

Update `state.md`:

- `Phase: 2`
- Append `web_research.md` to `FilesWritten`.
- Set `research_status: complete` (or `unavailable` per 1.2).

Read `phases/detection.md` and proceed.
